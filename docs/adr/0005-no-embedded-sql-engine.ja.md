# ADR 0005: 常時埋め込みの SQL エンジン無しで比較前整形を行う

- ステータス: Proposed（2026-09-27）
- 関連 Issue: ayame-editor/ayame-diff#126
- 関連作業: #116（順序非依存の等価判定）、#119（列マッピング）、
  #120（集計）、#121（合わせ方提案）、#128（非同期描画）、
  #19 / #60（パッケージング）

## 背景

比較は、データを整形して初めて意味を持つことが多い。列を落とし、行を並べ替え、
条件で絞り、場合によっては2つの抽出を結合する。SQL（`SELECT … ORDER BY …
WHERE …`、必要なら JOIN）で比較前整形を書ければ自然であり、順序非依存の等価判定
(#116)、列マッピング (#119)、集計 (#120)、合わせ方提案 (#121) と実装を共有できる。

このプロジェクトの優先順位は次の順である。

1. **実行時の快適さ。** 大きな入力でハングしたり OOM になったりしない。
2. **冗長性・可用性・絶対にクラッシュしない。** データ確認作業ではクラッシュが
   作業の損失に直結する。
3. **軽量。** 既定バイナリを太らせない。
4. **ビルドが現実的な時間で終わる。**

SQL は「あれば嬉しい」機能であり、上のどれか1つでも壊すなら受け入れられない。
また Go モジュールは標準ライブラリと、[ADR 0003](0003-encoding-dependency.ja.md)
に記録した `x/text` の例外以外に依存を持たないという制約がある。

## 選択肢

### A. DuckDB を常時埋め込む（`go-duckdb` など cgo）

不採用。cgo はビルドを大幅に遅くし、クロスコンパイルを難しくし、クラッシュ面を
増やす。優先順位 2・3・4 に真っ向から反する。これは issue で挙げられた懸念のとおり。

### B. オプションのビルドフィーチャ、または別バイナリのサイドカー

`ayame-diff-sql` バイナリ（または動的にロードするサイドカー）なら、既定バイナリは
純 Go のまま軽量でビルドも速く、クラッシュ面を本体から隔離できる。代償は配布・
更新経路の二重化であり、パッケージング (#19 / #60) とプロセス間受け渡しの設計を
同時に進める必要がある。

### C. PATH 上に external な `duckdb` / `sqlite3` があれば使う

埋め込みが無いため優先順位 2〜4 に影響せず、導入済みの利用者だけが恩恵を受ける。
課題はシェル実行の安全性で、`--pre`（prediffer shell）と認証の無い `serve` の懸念と
同じ注意が要る。この方向のプログレッシブエンハンスメントは許容できる。

### D. 既存パイプラインに依存ゼロの select / sort / filter DSL を足す

`select` / `order by` / `where` / `limit` 相当を自前実装する。フル SQL ではないが、
比較前整形の大部分を依存ゼロで賄え、#116・#120 と実装を共有でき、エンジンが既に
持つ spill（ストレージオフロード）に乗せられる。姉妹プロジェクト ayame-editor の
Rust core は sort/group/distinct/top/aggregate/spill を既に持ち、設計の参考になる。

## 決定

- **既定は D。** 依存ゼロの select / sort / filter 式を既存パイプライン内で実行し、
  ストレージオフロード（spill）の枠組みに従う。大規模入力でも UI を固まらせない。
- **フル SQL は B か C によるオプトインのみ。** 別バイナリのエクステンション、
  または PATH 上の外部 CLI。既定インストールの必須要件にはせず、既定バイナリに
  リンクしない。
- **A（常時埋め込み DuckDB）は不採用。**
- いずれの経路でも、比較前整形は UI をブロックせず、キャンセル可能で、
  黙って切り捨てるのではなく明示的に劣化すること。

## 影響

- 既定バイナリのサイズ・ビルド時間・クラッシュ面は現状のまま。
- SQL 風の機能はフル SQL より狭く始まる。JOIN やウィンドウ関数は D の対象外で、
  オプトイン経路に属する。
- #116・#119・#120・#121 は独自の絞り込み・並べ替えを増やさず、D の整形層の上に
  実装する。
- オプトイン経路は、配布・更新の設計が固まるまで出荷しない。

## 不採用の選択肢

- **常時埋め込み DuckDB (A):** ビルド時間・軽量性・クラッシュ面の優先順位に反する。
- **整形層の設計前に SQL を入れる:** #116 と #120 が必要とする実装を重複させ、
  データモデルを特定のクエリエンジンに固定する。
- **整形を一切しない:** 「比較前に絞って並べ替える」という issue の目的が未達のまま
  残る。
